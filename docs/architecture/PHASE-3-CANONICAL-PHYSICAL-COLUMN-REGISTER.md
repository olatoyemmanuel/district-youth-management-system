## 1. Authority and reconciliation

This register supersedes the Phase 2 65-table/617-column transcription as the current Phase 3 reconciliation candidate. It preserves the unchanged Phase 2 column rows and applies explicit corrections for owner-approved ODR-004 defaults, DDD-013, TBR-01, attendance exception evidence, category eligibility provenance, report data ownership and outbox linkage.

It is not executable DDL. Every row remains a design proposal pending exact physical ERD approval. Policy-dependent lifecycle values and authority-dependent features are not approved by this register.

## 4. Mandatory reconciliation notes

### 4.1 Authentication idempotency

`idempotency_records` uses the revised 23-column D13-PDR-01 model. Authenticated and pre-authentication rows are mutually exclusive. The request fingerprint is not part of the unique identity. The authenticated session FK proves session ownership through the composite tuple. The 24-hour response retention and 30-day compact tombstone remain on the same row.

### 4.2 Pre-authentication context

The browser context secret is cryptographically random and only its digest is stored. Cookie contract: host-only, `Path=/api/v1/auth`, Secure, HttpOnly, SameSite=Lax, Max-Age 600 seconds. The server context expires no later than 10 minutes. The context row may remain as a non-secret identity stub while an idempotency tombstone references it; the secret digest is erased after expiry/consumption/revocation.

Non-browser clients remain unsupported until a separate binding contract is approved.

### 4.3 Attendance registration exception

A row without `registration_id` must carry the granting actor, non-empty reason and grant timestamp. The CHECK validates completeness, not the actor's permission. Authorization remains application/domain enforcement.

### 4.4 Organizational scope

Departments are district-owned. Events have a required district boundary and optional church owner. A church-owned event's church must belong to the same district through a composite FK. Departments may be linked as organizers, not owners.

### 4.5 Reporting scope and data owner

Every report run is district-bound. A report run may be district, church or department scoped; GLOBAL and cross-district scopes are excluded. Church and department references must match the same district. Each report definition references an approved `report_data_owners` catalogue entry and has a classification. The catalogue remains unpopulated until ODR-013 delegated authorities identify owners.

### 4.6 Category eligibility provenance

`member_category_eligibility_rules` stores versioned official rules without inventing age, class or qualification criteria. ODR-001 remains open. Category assignment records may reference the exact rule used; active category assignments must not be issued against an unapproved or absent rule.

## 5. Defaults and timestamps

- UUID primary keys use the approved PostgreSQL 15 `gen_random_uuid()` candidate.
- Creation instants use `transaction_timestamp()` where explicitly shown.
- Mutable `updated_at` columns are maintained by a database trigger; application callers do not backdate them.
- Business effective dates, approvals, event times and provider times remain separate facts.
- No lifecycle status receives an implicit default.
- Money remains exact `numeric`; the existing precision/scale proposal remains subject to finance authority confirmation.

## 6. Approval boundary

This register is the canonical Phase 3 column candidate for review. It does not approve the physical ERD, PostgreSQL DDL, Prisma models, migrations, database objects, seeds, APIs or application code. The final physical design must be approved by exact version/hash, followed by separate implementation authorization.
