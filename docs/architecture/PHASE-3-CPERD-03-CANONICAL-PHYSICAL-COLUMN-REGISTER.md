## 1. Authority
This is a CPERD-03 successor candidate derived from the CPERD-02 canonical column register. CPERD-01 and CPERD-02 historical artifacts remain unchanged. This register applies the current DYMS 1.0 scope exclusions, adds the Federation parent, and removes transfer-only membership actor fields.
No row in this register is executable DDL or an implementation instruction. Candidate type/default/key details remain subject to cross-register reconciliation and owner approval.

## 3. Default and type policy
The inherited source contained unresolved default entries. This candidate now replaces each such entry with an explicit default policy. UUID primary keys use application-generated UUIDv7 with no database default. created_at uses a proposed trusted database transaction_timestamp() default. updated_at uses that trusted insert-time default plus a trusted update-time trigger proposal. Other values have no database default and must be supplied by the authorized application workflow; nullable values remain NULL when absent. These are physical-design proposals requiring owner approval, not permission to implement.
OD-02 requires application-generated UUIDv7 using a verified generator and PostgreSQL native UUID storage. Inherited UUID rows must be reconciled to this generation contract. OD-07 requires stable technical states to use PostgreSQL ENUM, business categories to use lookup tables, and explicit nullability/default policy. OD-08 governs every instant and timezone-sensitive field.
## 4. Federation and district additions
The Federation candidate uses six columns: id, code, name, status, created_at, updated_at. Districts gain a required federation_id. The exact federation code normalization/uniqueness scope, status ENUM values, timestamp default/update mechanism, composite ownership FK, and final index names remain open technical specifications. The candidate names shown below are not approved constraints.
