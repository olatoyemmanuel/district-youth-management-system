# DYMS Phase 2 Canonical Index Inventory

**Status:** Consolidated document-level proposal, not approved for implementation  
**Scope:** DYMS v1.0, Sango District  
**Branch:** `phase-1/requirements-consolidation`  
**Implementation:** NOT AUTHORIZED

## 1. Purpose and authority

This document consolidates the named unique, partial-unique, FK-supporting, and workload/access index proposals from:

- [Foreign-Key and Column Register](./PHASE-2-FOREIGN-KEY-AND-COLUMN-REGISTER.md), Sections 5.6 and 5.7.
- [Medium-Severity Relational Integrity Remediation](./PHASE-2-MEDIUM-SEVERITY-RELATIONAL-INTEGRITY-REMEDIATION.md), Sections 4.1 and 4.2.

It is the single document-level name inventory for those proposals. It does not establish that each index is necessary, non-redundant, executable, performant, or approved. Primary-key indexes generated by PostgreSQL are outside this named proposal inventory.

Six entries are classified POLICY BLOCKED and are not DDL-ready: five lifecycle-dependent partial unique indexes and one normalized-email index whose deterministic expression/storage is not defined. The remaining 208 entries have concrete key columns and declared predicates. This classification preserves unresolved policy questions without treating placeholders as executable indexes.

## 4. Reconciliation rules and limitations

- A name appearing in both source catalogues is represented once. Its source column identifies both catalogues.
- FK support indexes must begin with the complete ordered source tuple for a composite FK. A workload index with only a shared first column is not treated as complete composite-FK coverage.
- A wider index may support a single-column FK by left prefix only when that FK column is the leftmost key.
- Partial indexes must retain a predicate compatible with the source FK nullability and the intended access path.
- Lifecycle-dependent partial-unique predicates remain blocked until their state values and transition rules are approved.
- `uq_financial_accounts_owner_code` currently denotes an owner-specific partial-uniqueness proposal. The physical implementation must give every actual index its own unique PostgreSQL name; this logical catalogue label must not be treated as permission to create multiple same-named indexes.
- The inventory is derived from design documents. No PostgreSQL catalogue, DDL parser, query plan, workload benchmark, or database was used to validate these proposals.

## 5. Approval boundary

This inventory does not approve the physical database design or authorize SQL DDL, Prisma schema changes, migrations, database objects, generated clients, seeds, or application code. DFR-001 through DFR-006 and the approved conceptual ERD remain preserved. Separate explicit approval of the complete physical design and separate implementation authorization remain mandatory.
