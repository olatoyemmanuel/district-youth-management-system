**Status:** Working physical-design proposal for project-owner review  
**Scope:** DYMS v1.0, Sango District  
**Approved logical source:** Conceptual ERD commit `25f2813e0256d9472daded45657dfb7ac9f70a43`  
**Current review branch:** `phase-1/requirements-consolidation`  
**Implementation status:** NOT AUTHORIZED

## 1. Purpose and boundary

This document translates the approved conceptual ERD into a PostgreSQL-oriented relational design proposal. It proposes table names, column types, keys, constraints, indexes, and integrity strategies for review.

This is a design document only. It does not create or modify `backend/prisma/schema.prisma`, generate Prisma models, create migrations, execute SQL, or alter a database. The project owner must separately approve the physical design and explicitly authorize implementation.

The conceptual ERD remains the logical source of truth. This document must not silently settle official church policy or accounting rules that remain open.

## 2. Design principles

1. PostgreSQL is the system of record. Prisma is a persistence mapping tool, not the authority for database integrity.
2. Use UUID primary keys generated by the database or application using a cryptographically secure UUIDv4 strategy. Do not expose sequential identifiers as public identifiers.
3. Use `timestamptz` for instants. Store instants in UTC. Store an IANA timezone name separately for events and other locally scheduled activity.
4. Use `date` for calendar-only values such as birth date, term dates, and accounting period boundaries where a time-of-day is not meaningful.
5. Use `numeric(p,s)` for money. Never use `real`, `double precision`, or JavaScript floating-point values for authoritative financial calculations.
6. Use `text` with validation and controlled reference tables for evolving codes. Avoid PostgreSQL ENUM for business states that may need governed extension.
7. Use explicit foreign keys. Do not use an unchecked polymorphic `scope_type + scope_id` pair for organizational ownership.
8. Preserve history through separate records and lifecycle transitions. Do not overwrite or delete posted financial facts, appointment history, category history, or approved corrections.
9. Use database constraints for invariants that must survive concurrent requests. Application validation alone is insufficient.
10. Apply least-privilege database roles. Runtime application credentials must not own tables or have unrestricted DDL privileges.
11. Never store raw passwords, access tokens, refresh tokens, reset tokens, provider secrets, or session cookies.
12. All sensitive state transitions must have an auditable actor, reason where required, and correlation/idempotency context.

## 3. PostgreSQL conventions

| Concern | Proposal |
|---|---|
| Primary key | `uuid`, primary key, generated with `gen_random_uuid()` or trusted application UUID generation |
| Foreign key | Same UUID type, explicit named FK |
| Short code | `varchar(50)` or `text` with unique constraint and normalization |
| Human name/title | `varchar(200)` or `text`, bounded at API validation |
| Description/notes | `text`, with size limits at API boundary |
| Email/login | Normalized value plus a unique normalized column or unique index; case-folding policy must be consistent |
| Phone | Normalized E.164 string where available; verification state separate |
| Money | `numeric(19,4)` pending accounting policy; account currency fixed |
| Currency | `char(3)` referencing controlled currency code |
| Count/attempt | `integer` with non-negative CHECK |
| Effective interval | `timestamptz` start and nullable end, or `daterange` only where date-only semantics are approved |
| Status | `varchar(30)` plus CHECK or governed lookup table |
| JSON | `jsonb` only for bounded provider metadata or versioned non-authoritative payloads, never as a substitute for relational business fields |
| Optimistic concurrency | `bigint` version column on high-contention mutable aggregates where needed |
| Created/updated | `created_at timestamptz NOT NULL`; `updated_at timestamptz NOT NULL` on mutable records |
| Deletion | No generic soft-delete field by default. Use domain status, closure, revocation, reversal, retention action |

Use explicit schema namespaces only if the deployment/Prisma mapping decision is approved. The initial recommendation is a single `public` schema with domain-prefixed table names or consistent plural snake_case names. Pick one naming convention before implementation and apply it uniformly.

## 4. Organizational scope and referential integrity

### 4.1 Supported scope targets

DYMS v1.0 supports District, Church, and Department scope. The physical model must not accept arbitrary scope strings or unvalidated UUIDs.

For records whose owner is either a district or a church, use nullable `district_id` and `church_id` foreign keys with a CHECK requiring exactly one to be non-null. For records whose owner can be a department, add `department_id` as a third nullable FK and require exactly one permitted owner. Do not add department ownership to finance accounts unless the finance policy explicitly approves it.

Example invariant, for a district-or-church-owned row:

```sql
CHECK (num_nonnulls(district_id, church_id) = 1)
```

A department row should itself reference its owning district and, only if the approved organizational model requires it, an optional church. A department-scoped role assignment references the department row directly. Application authorization must still verify that the department belongs to the same district/church context as the operation.

### 4.2 Cross-scope integrity

Where a child references both a parent and a scope, simple independent FKs are not enough to prove they match. Use composite unique keys on the parent, such as `UNIQUE (event_id, district_id)`, and composite FKs from the child where the schema shape permits. Otherwise enforce the cross-row rule in a database trigger or a transactionally locked domain service, with an explicit test. Prefer declarative composite constraints over triggers.

Do not use a generic `scope_type + scope_id` field as the only relationship. A generic target reference is acceptable only for append-only audit metadata where the target can be historical or from multiple bounded contexts and is not used as a business ownership FK.

## 5. Relational catalogue and column proposals

The table list below is the proposed physical mapping. Columns marked nullable are optional only for the stated reason. All IDs are UUID unless noted. Every table receives a named primary key and explicit FK constraints. Audit timestamps and actor columns are included where appropriate; the list focuses on domain-specific columns.

### 5.1 Identity, accounts, and sessions

#### `user_accounts`
- `id uuid PK`
- `login_identifier text NOT NULL`, normalized consistently; unique
- `email text NULL`, normalized; unique when present
- `phone_e164 varchar(20) NULL`, unique when present
- `password_hash text NOT NULL`
- `status varchar(24) NOT NULL`, CHECK against proposed states `PENDING`, `ACTIVE`, `SUSPENDED`, `CLOSED`
- `email_verified_at timestamptz NULL`, `phone_verified_at timestamptz NULL`
- `last_login_at timestamptz NULL`, `created_at`, `updated_at`
- Do not place access/refresh/reset tokens in this table.

#### `members`
- `id uuid PK`
- `user_account_id uuid NOT NULL UNIQUE FK user_accounts(id)`
- `member_number varchar(50) NOT NULL UNIQUE`
- `first_name text NOT NULL`, `last_name text NOT NULL`, `other_names text NULL`
- `date_of_birth date NULL` until collection is justified and policy approved
- `status varchar(24) NOT NULL`
- `created_at`, `updated_at`
- Enforce exactly one account per member and at most one member per account. No guardian relationship table and no account delegation fields.

#### `auth_sessions`
- `id uuid PK`, `user_account_id uuid NOT NULL FK`
- `refresh_token_hash text NOT NULL`, unique
- `created_at timestamptz NOT NULL`, `last_activity_at timestamptz NOT NULL`
- `inactivity_expires_at timestamptz NOT NULL`, `absolute_expires_at timestamptz NOT NULL`
- `revoked_at timestamptz NULL`, `revocation_reason text NULL`
- `user_agent_summary text NULL`, `ip_address inet NULL` subject to retention/privacy review
- CHECK: inactivity expiry <= absolute expiry; revoked session cannot be refreshed.
- Index: `(user_account_id, revoked_at, absolute_expires_at)`.
- Refresh rotation history should be held in a separate `auth_session_tokens` table if token reuse detection needs prior-token fingerprints. Never persist raw tokens.

#### `auth_session_tokens`
- `id uuid PK`, `auth_session_id uuid NOT NULL FK auth_sessions(id)`
- `token_hash text NOT NULL UNIQUE`, `issued_at timestamptz NOT NULL`, `consumed_at timestamptz NULL`, `revoked_at timestamptz NULL`
- Keep only the minimum token-fingerprint history required for reuse detection. Retention is security-policy dependent.
- Concurrent rotation must be atomic and serialize on the session row.

#### `password_reset_tokens`
- `id uuid PK`, `user_account_id uuid NOT NULL FK`
- `token_hash text NOT NULL UNIQUE`, `created_at timestamptz NOT NULL`, `expires_at timestamptz NOT NULL`, `consumed_at timestamptz NULL`
- CHECK expiry after creation; single-use enforced by conditional update/transaction.
- Never store raw reset token.

### 5.2 Membership and organization

#### `districts`
- `id uuid PK`, `code varchar(50) NOT NULL UNIQUE`, `name text NOT NULL`, `timezone text NOT NULL`, `status varchar(20) NOT NULL`.

#### `churches`
- `id uuid PK`, `district_id uuid NOT NULL FK districts(id)`
- `code varchar(50) NOT NULL`, `name text NOT NULL`, `status varchar(20) NOT NULL`
- `UNIQUE (district_id, code)`, `UNIQUE (id, district_id)`.

#### `member_categories`
- `id uuid PK`, `code varchar(40) NOT NULL UNIQUE`, `name text NOT NULL`, `is_active boolean NOT NULL`
- Seed Adventurer, Pathfinder, Senior Youth. Do not add Master Guide as a member category.

#### `member_category_assignments`
- `id uuid PK`, `member_id uuid NOT NULL FK members(id)`, `member_category_id uuid NOT NULL FK member_categories(id)`
- `assigned_by_user_account_id uuid NOT NULL FK user_accounts(id)`
- `effective_from timestamptz NOT NULL`, `effective_to timestamptz NULL`
- `status varchar(20) NOT NULL`, `reason text NULL`, `evidence_reference text NULL`
- CHECK effective_to is null or greater than effective_from.
- Partial unique index: one current active assignment per member, e.g. unique `member_id` where status is active and effective_to is null.
- Eligibility criteria and category transition approval policy remain open. Do not encode age thresholds.

#### `church_memberships`
- `id uuid PK`, `member_id uuid NOT NULL FK members(id)`, `church_id uuid NOT NULL FK churches(id)`
- `status varchar(24) NOT NULL`, `effective_from timestamptz NOT NULL`, `effective_to timestamptz NULL`
- `initiated_by_user_account_id uuid NOT NULL FK user_accounts(id)`
- `accepted_by_user_account_id uuid NULL FK user_accounts(id)`, `approved_by_user_account_id uuid NULL FK user_accounts(id)`
- `created_at`, `updated_at`
- CHECK effective interval.
- Partial unique index: one current approved membership per member where status/effective interval marks current.
- Transfer approval must close old and create new membership in one transaction.

#### `church_transfer_requests`
- `id uuid PK`, `member_id uuid NOT NULL FK members(id)`
- `source_church_id uuid NOT NULL FK churches(id)`, `receiving_church_id uuid NOT NULL FK churches(id)`
- `requested_by_user_account_id uuid NOT NULL FK user_accounts(id)`
- `status varchar(24) NOT NULL`, `requested_at timestamptz NOT NULL`
- `receiving_decided_by_user_account_id uuid NULL FK user_accounts(id)`, `receiving_decided_at timestamptz NULL`, `receiving_decision text NULL`
- `district_decided_by_user_account_id uuid NULL FK user_accounts(id)`, `district_decided_at timestamptz NULL`, `district_decision text NULL`
- `approved_effective_at timestamptz NULL`, `cancellation_reason text NULL`
- CHECK source and receiving church differ.
- A partial unique index for one pending transfer per member is recommended, but cancellation/rejection semantics need owner policy confirmation before the predicate is finalized.

#### `departments`
- `id uuid PK`, `district_id uuid NOT NULL FK districts(id)`
- `church_id uuid NULL FK churches(id)` only for formally church-owned department instances
- `code varchar(50) NOT NULL`, `name text NOT NULL`, `status varchar(20) NOT NULL`
- Use separate uniqueness rules for district-level and church-level department codes. Validate church belongs to district.

#### `department_eligibility_rules`
- `id uuid PK`, `department_id uuid NOT NULL FK departments(id)`, `version varchar(40) NOT NULL`, `description text NOT NULL`, `source_authority text NULL`, `evidence_requirements jsonb NULL`, `effective_from timestamptz NOT NULL`, `effective_to timestamptz NULL`, `status varchar(20) NOT NULL`.
- Unique `(department_id, version)`. JSONB is limited to descriptive evidence metadata, not member eligibility decisions.
- Do not activate a rule until its official source and approving authority are recorded.

#### `department_memberships`
- `id uuid PK`, `member_id uuid NOT NULL FK members(id)`, `department_id uuid NOT NULL FK departments(id)`
- `requested_by_user_account_id uuid NOT NULL FK user_accounts(id)`
- `approved_by_user_account_id uuid NULL FK user_accounts(id)`, `ended_by_user_account_id uuid NULL FK user_accounts(id)`
- `eligibility_rule_id uuid NULL FK department_eligibility_rules(id)` to retain the rule version considered, where a rule exists.
- `status varchar(24) NOT NULL`, `requested_at timestamptz NOT NULL`, `effective_from timestamptz NULL`, `effective_to timestamptz NULL`, `end_reason text NULL`
- Partial unique index prevents duplicate active membership for member/department.
- Department eligibility, renewal and transfer behavior remain policy gaps.

### 5.3 Leadership and authorization

#### `positions`
- `id uuid PK`, `department_id uuid NULL FK departments(id)`, `code varchar(50) NOT NULL`, `title text NOT NULL`, `status varchar(20) NOT NULL`
- Position code uniqueness must include department and scope if the same title occurs in different departments.

#### `appointments`
- `id uuid PK`, `position_id uuid NOT NULL FK positions(id)`, `appointee_member_id uuid NOT NULL FK members(id)`
- Explicit scope FKs: `district_id uuid NULL`, `church_id uuid NULL`, `department_id uuid NULL`; exactly one permitted scope FK must be populated and each FK must be valid.
- `appointing_authority_user_account_id uuid NOT NULL FK user_accounts(id)`, `approved_by_user_account_id uuid NOT NULL FK user_accounts(id)`
- `term_start date NOT NULL`, `term_end date NOT NULL`, `effective_from timestamptz NOT NULL`, `effective_to timestamptz NULL`
- `status varchar(24) NOT NULL`, `appointment_reason text NULL`, `termination_reason text NULL`, `approved_at timestamptz NOT NULL`
- CHECK term_end >= term_start and effective interval valid.
- Prevent overlapping active appointment for same position and exact scope. PostgreSQL exclusion constraints using `btree_gist` and a range expression are a candidate, subject to scope-specific implementation review. A partial unique index only prevents identical current rows, not arbitrary overlapping intervals.
- Acting appointments and overlap exceptions are not enabled in this proposal.

#### `roles`
- `id uuid PK`, `code varchar(60) NOT NULL UNIQUE`, `name text NOT NULL`, `status varchar(20) NOT NULL`.

#### `permissions`
- `id uuid PK`, `code varchar(100) NOT NULL UNIQUE`, `resource text NOT NULL`, `action text NOT NULL`, `description text NULL`, `status varchar(20) NOT NULL`
- Permission catalogue and scope support matrix must be approved before production seeds.

#### `role_permissions`
- `id uuid PK`, `role_id uuid NOT NULL FK roles(id)`, `permission_id uuid NOT NULL FK permissions(id)`
- `effect varchar(10) NOT NULL CHECK (effect = 'ALLOW')`, `created_at timestamptz NOT NULL`
- `UNIQUE (role_id, permission_id)`. Explicit DENY remains a separate scoped entity, not a role permission effect.

#### `user_role_assignments`
- `id uuid PK`, `user_account_id uuid NOT NULL FK user_accounts(id)`, `role_id uuid NOT NULL FK roles(id)`
- Explicit nullable `district_id`, `church_id`, `department_id` FKs; exactly one valid scope target.
- `granted_by_user_account_id uuid NOT NULL FK user_accounts(id)`, `effective_from timestamptz NOT NULL`, `effective_to timestamptz NULL`, `status varchar(20) NOT NULL`, `reason text NULL`
- Prevent self-grant in the service transaction and audit it. Use constraints for scope and interval.

#### `appointment_role_links`
- `id uuid PK`, `appointment_id uuid NOT NULL FK appointments(id)`, `role_id uuid NOT NULL FK roles(id)`
- `mapping_version varchar(40) NOT NULL`, `created_at timestamptz NOT NULL`, `created_by_user_account_id uuid NOT NULL FK user_accounts(id)`
- `UNIQUE (appointment_id, role_id, mapping_version)`. Only active approved appointments produce effective role grants.

#### `access_denies`
- `id uuid PK`, `target_user_account_id uuid NOT NULL FK user_accounts(id)`, `permission_id uuid NOT NULL FK permissions(id)`
- Exactly one of `district_id`, `church_id`, `department_id` populated as valid scope FKs.
- `issued_by_user_account_id uuid NOT NULL FK user_accounts(id)`, `reviewed_by_user_account_id uuid NULL FK user_accounts(id)`
- `reason text NOT NULL`, `effective_from timestamptz NOT NULL`, `expires_at timestamptz NULL`, `review_due_at timestamptz NULL`, `status varchar(20) NOT NULL`, `revoked_at timestamptz NULL`, `revocation_reason text NULL`
- Service-level checks prevent target actor from issuing, approving, modifying, or revoking own deny. Review and audit are mandatory.

#### `role_conflict_rules` and `role_conflict_reviews`
- Rules: `id uuid PK`, `role_a_id uuid NOT NULL FK roles(id)`, `role_b_id uuid NOT NULL FK roles(id)`, `outcome varchar(24) NOT NULL`, `version varchar(40) NOT NULL`, `effective_from timestamptz NOT NULL`, `effective_to timestamptz NULL`, `rationale text NOT NULL`.
- Canonicalize role pair ordering and enforce unique `(role_a_id, role_b_id, version)`; disallow role_a = role_b unless an explicit self-conflict rule is approved.
- Reviews: `id uuid PK`, `user_account_id uuid NOT NULL FK user_accounts(id)`, `role_conflict_rule_id uuid NOT NULL FK role_conflict_rules(id)`, `reviewed_by_user_account_id uuid NOT NULL FK user_accounts(id)`, `decision varchar(24) NOT NULL`, `reason text NOT NULL`, `reviewed_at timestamptz NOT NULL`, `effective_from timestamptz NULL`, `effective_to timestamptz NULL`.
- A review-required role combination is not effective until an independent authorized review exists.

### 5.4 Events and attendance

#### `events`
- `id uuid PK`, `title text NOT NULL`, `description text NULL`, `event_type varchar(40) NOT NULL`, `status varchar(24) NOT NULL`
- Explicit owner FKs: exactly one of `district_id`, `church_id`, `department_id` as permitted by event type and approved policy.
- `venue text NULL`, `starts_at timestamptz NOT NULL`, `ends_at timestamptz NOT NULL`, `timezone text NOT NULL`
- `registration_opens_at timestamptz NULL`, `registration_closes_at timestamptz NULL`, `capacity integer NULL CHECK (capacity IS NULL OR capacity >= 0)`
- `created_by_user_account_id uuid NOT NULL FK user_accounts(id)`, `created_at`, `updated_at`, `cancelled_at timestamptz NULL`, `cancellation_reason text NULL`
- CHECK ends_at > starts_at; registration close >= open when both exist.
- District event publication requires approved district decision. Local event approval remains open.

#### `event_approvals`
- `id uuid PK`, `event_id uuid NOT NULL FK events(id)`, `reviewer_user_account_id uuid NOT NULL FK user_accounts(id)`
- `stage varchar(40) NOT NULL`, `decision varchar(24) NOT NULL`, `reason text NULL`, `decided_at timestamptz NOT NULL`
- Keep every decision. Do not store only the latest approval state.

#### `event_change_records`
- `id uuid PK`, `event_id uuid NOT NULL FK events(id)`, `requested_by_user_account_id uuid NOT NULL FK user_accounts(id)`, `approved_by_user_account_id uuid NULL FK user_accounts(id)`
- `change_type varchar(40) NOT NULL`, `previous_values jsonb NOT NULL`, `proposed_values jsonb NOT NULL`, `reason text NOT NULL`, `status varchar(20) NOT NULL`, `requested_at timestamptz NOT NULL`, `decided_at timestamptz NULL`.
- JSONB snapshots are restricted to allowlisted event fields and must not contain secrets or unrelated personal data. Significant changes retain request and approval history.

#### `event_registrations`
- `id uuid PK`, `event_id uuid NOT NULL FK events(id)`, `member_id uuid NOT NULL FK members(id)`
- `status varchar(24) NOT NULL`, `registered_at timestamptz NOT NULL`, `registration_channel varchar(24) NOT NULL`, `cancelled_at timestamptz NULL`, `cancellation_reason text NULL`
- Unique active registration per event/member via partial unique index. Capacity enforcement must lock or atomically update an event capacity counter to avoid oversubscription.

#### `event_sessions`
- `id uuid PK`, `event_id uuid NOT NULL FK events(id)`, `name text NOT NULL`
- `starts_at timestamptz NOT NULL`, `ends_at timestamptz NOT NULL`, `timezone text NOT NULL`, `venue text NULL`, `status varchar(20) NOT NULL`
- `UNIQUE (id, event_id)`; CHECK ends_at > starts_at.

#### `attendance_records`
- `id uuid PK`, `event_id uuid NOT NULL FK events(id)`, `event_session_id uuid NULL`, `member_id uuid NOT NULL FK members(id)`
- `registration_id uuid NULL FK event_registrations(id)`, `recorded_by_user_account_id uuid NOT NULL FK user_accounts(id)`
- `attendance_status varchar(24) NOT NULL`, `recorded_at timestamptz NOT NULL`, `method varchar(20) NOT NULL`, `note text NULL`
- Composite FK `(event_session_id, event_id)` to `event_sessions(id, event_id)` ensures session belongs to event.
- Event-level mode: `event_session_id IS NULL`, unique `(event_id, member_id)` among valid records.
- Session-level mode: `event_session_id IS NOT NULL`, unique `(event_session_id, member_id)` among valid records.
- The policy against mixing event-level and session-level attendance for the same member/event requires a transactionally serialized check or a normalized attendance-subject design. A pair of partial unique indexes alone cannot enforce cross-mode exclusion.
- Registration prerequisite remains unresolved; nullable registration FK preserves the open policy.

#### `attendance_corrections`
- `id uuid PK`, `attendance_record_id uuid NOT NULL FK attendance_records(id)`
- `requested_by_user_account_id uuid NOT NULL FK user_accounts(id)`, `approved_by_user_account_id uuid NULL FK user_accounts(id)`
- `previous_status varchar(24) NOT NULL`, `proposed_status varchar(24) NOT NULL`, `reason text NOT NULL`, `status varchar(20) NOT NULL`, `requested_at timestamptz NOT NULL`, `approved_at timestamptz NULL`
- Approved correction updates the effective attendance state in the same transaction and preserves the correction row plus audit event.

### 5.5 Finance

#### `financial_accounts`
- `id uuid PK`, `account_code varchar(50) NOT NULL`, `name text NOT NULL`
- Exactly one owner FK: `district_id uuid NULL` or `church_id uuid NULL`; CHECK `num_nonnulls(district_id, church_id) = 1`.
- `currency_code char(3) NOT NULL FK currencies(code)`, `status varchar(20) NOT NULL`, `opened_at timestamptz NOT NULL`, `closed_at timestamptz NULL`
- Unique account code within owning scope. Account currency is immutable after first posted transaction; changing currency requires a new account.

#### `currencies`
- `code char(3) PK`, `name text NOT NULL`, `minor_unit smallint NOT NULL CHECK (minor_unit BETWEEN 0 AND 4)`, `is_active boolean NOT NULL`.
- Seed NGN. Other currencies require explicit approval.

#### `financial_transactions`
- `id uuid PK`, `financial_account_id uuid NOT NULL FK financial_accounts(id)`
- `transaction_type varchar(30) NOT NULL`, `reference varchar(80) NOT NULL`, `description text NOT NULL`
- `amount numeric(19,4) NOT NULL`, `currency_code char(3) NOT NULL`, `status varchar(24) NOT NULL`
- `transaction_date date NOT NULL`, `submitted_by_user_account_id uuid NOT NULL FK user_accounts(id)`
- `submitted_at timestamptz NULL`, `rejection_reason text NULL`, `posted_at timestamptz NULL`, `posted_by_user_account_id uuid NULL FK user_accounts(id)`
- Composite FK or trigger/service validation ensures transaction currency equals account currency. Amount sign convention remains blocked by accounting policy. Do not add a CHECK `amount > 0` until debit/credit semantics are approved.
- Unique `(financial_account_id, reference)`.

#### `transaction_revisions`
- `id uuid PK`, `financial_transaction_id uuid NOT NULL FK financial_transactions(id)`, `revision_number integer NOT NULL CHECK (revision_number > 0)`
- `requested_by_user_account_id uuid NOT NULL FK user_accounts(id)`, `reason text NOT NULL`, `previous_snapshot jsonb NOT NULL`, `proposed_snapshot jsonb NOT NULL`, `status varchar(20) NOT NULL`, `created_at timestamptz NOT NULL`, `decided_at timestamptz NULL`.
- Unique `(financial_transaction_id, revision_number)`. Snapshots are allowlisted and preserve submitted transaction history; posted transactions are corrected only by reversal, not revision.

#### `transaction_approvals`
- `id uuid PK`, `financial_transaction_id uuid NOT NULL FK financial_transactions(id)`, `approver_user_account_id uuid NOT NULL FK user_accounts(id)`
- `decision varchar(20) NOT NULL`, `reason text NULL`, `approval_level integer NULL`, `decided_at timestamptz NOT NULL`
- CHECK approver differs from submitter must be enforced by a trigger or transactionally locked service because it compares rows. Preserve all decisions.

#### `payments`
- `id uuid PK`, `financial_transaction_id uuid NOT NULL FK financial_transactions(id)`, `provider_id uuid NULL FK integration_providers(id)`
- `payment_reference varchar(100) NOT NULL UNIQUE`, `provider_reference varchar(150) NULL`, `amount numeric(19,4) NOT NULL`, `currency_code char(3) NOT NULL`
- `status varchar(24) NOT NULL`, `initiated_at timestamptz NOT NULL`, `confirmed_at timestamptz NULL`, `failure_reason text NULL`
- Do not infer partial settlement or refund behavior. Store attempts distinctly; reconciliation required for uncertain outcomes.

#### `transaction_reversals`
- `id uuid PK`, `original_transaction_id uuid NOT NULL FK financial_transactions(id)`, `reversal_transaction_id uuid NOT NULL UNIQUE FK financial_transactions(id)`
- `initiated_by_user_account_id uuid NOT NULL FK user_accounts(id)`, `approved_by_user_account_id uuid NULL FK user_accounts(id)`
- `reason text NOT NULL`, `status varchar(24) NOT NULL`, `created_at timestamptz NOT NULL`, `posted_at timestamptz NULL`
- CHECK original and reversal transaction differ. Prevent duplicate full reversal. Cumulative partial reversal checks require approved partial-reversal policy and serialized transaction.

#### `budgets` and `budget_lines`
- Budget: `id uuid PK`, explicit district or church owner FKs, `period_start date NOT NULL`, `period_end date NOT NULL`, `currency_code char(3) FK currencies`, `status varchar(20) NOT NULL`, `approved_by_user_account_id uuid NULL FK user_accounts(id)`.
- Lines: `id uuid PK`, `budget_id uuid NOT NULL FK budgets(id)`, `category_code varchar(50) NOT NULL`, `description text NOT NULL`, `allocated_amount numeric(19,4) NOT NULL`, `revised_amount numeric(19,4) NULL`.
- Budget controls remain inactive until approved policy defines enforcement, revision authority, and variance treatment.

### 5.6 Credentials

#### `credential_definitions`
- `id uuid PK`, `code varchar(60) NOT NULL`, `issuing_authority text NOT NULL`, `issuer_scope_district_id uuid NULL FK districts(id)`, `issuer_scope_church_id uuid NULL FK churches(id)`, `status varchar(20) NOT NULL`.
- Definition versions are separate rows to preserve rule changes.

#### `credential_definition_versions`
- `id uuid PK`, `credential_definition_id uuid NOT NULL FK credential_definitions(id)`, `version varchar(40) NOT NULL`, `title text NOT NULL`, `requirements_reference text NOT NULL`, `validity_policy varchar(24) NOT NULL`, `validity_duration interval NULL`, `effective_from timestamptz NOT NULL`, `effective_to timestamptz NULL`, `approved_by_user_account_id uuid NULL FK user_accounts(id)`
- CHECK validity duration is null unless policy requires a duration. Official source and expiry rules must be verified before active issue.

#### `credential_issuances`
- `id uuid PK`, `member_id uuid NOT NULL FK members(id)`, `credential_definition_version_id uuid NOT NULL FK credential_definition_versions(id)`
- `issuer_user_account_id uuid NOT NULL FK user_accounts(id)`, `approved_by_user_account_id uuid NOT NULL FK user_accounts(id)`, `prior_issuance_id uuid NULL FK credential_issuances(id)`
- `issued_at timestamptz NOT NULL`, `valid_from timestamptz NOT NULL`, `valid_until timestamptz NULL`, `status varchar(24) NOT NULL`, `revoked_at timestamptz NULL`, `revocation_reason text NULL`
- CHECK valid_until is null or >= valid_from. No expiry unless definition version requires it.

#### `credential_evidence`
- `id uuid PK`, `credential_issuance_id uuid NOT NULL FK credential_issuances(id)`, `submitted_by_user_account_id uuid NOT NULL FK user_accounts(id)`, `verified_by_user_account_id uuid NULL FK user_accounts(id)`
- `evidence_type varchar(40) NOT NULL`, `object_storage_key text NOT NULL`, `submitted_at timestamptz NOT NULL`, `verified_at timestamptz NULL`, `verification_status varchar(24) NOT NULL`
- Store file bytes in protected object storage, not PostgreSQL large objects by default. Keep only opaque storage key and minimal metadata.

### 5.7 Notifications and external integrations

#### `notification_templates`
- `id uuid PK`, `code varchar(80) NOT NULL`, `version integer NOT NULL`, `channel varchar(20) NOT NULL`, `locale varchar(20) NOT NULL`, `content text NOT NULL`, `status varchar(20) NOT NULL`
- Unique `(code, version, channel, locale)`.

#### `notification_preferences`
- `id uuid PK`, `user_account_id uuid NOT NULL FK user_accounts(id)`, `channel varchar(20) NOT NULL`, `category varchar(40) NOT NULL`, `consent_state varchar(20) NOT NULL`, `effective_from timestamptz NOT NULL`, `effective_to timestamptz NULL`, `source text NULL`
- Preserve preference history. Do not infer consent for optional channels.

#### `notifications`
- `id uuid PK`, `logical_key varchar(160) NOT NULL UNIQUE`, `template_id uuid NULL FK notification_templates(id)`
- `category varchar(40) NOT NULL`, `payload_reference text NULL`, `status varchar(24) NOT NULL`, `created_at timestamptz NOT NULL`, `scheduled_at timestamptz NULL`
- Store minimal message payload or a protected reference. Avoid copying sensitive business records into notification payload.

#### `notification_recipients`
- `id uuid PK`, `notification_id uuid NOT NULL FK notifications(id)`, `user_account_id uuid NOT NULL FK user_accounts(id)`
- `destination_snapshot text NULL`, `preference_decision varchar(24) NOT NULL`, `status varchar(24) NOT NULL`, `UNIQUE (notification_id, user_account_id)`.
- Destination snapshots require privacy/retention approval and should be minimized.

#### `integration_providers`
- `id uuid PK`, `provider_code varchar(60) NOT NULL UNIQUE`, `service_type varchar(30) NOT NULL`, `status varchar(20) NOT NULL`, `configuration_reference text NULL`
- No secret/token/password fields. Secret values remain in a secrets manager.

#### `notification_deliveries`
- `id uuid PK`, `notification_recipient_id uuid NOT NULL FK notification_recipients(id)`, `provider_id uuid NOT NULL FK integration_providers(id)`
- `attempt_number integer NOT NULL CHECK (attempt_number > 0)`, `provider_message_id text NULL`, `status varchar(24) NOT NULL`, `accepted_at timestamptz NULL`, `delivered_at timestamptz NULL`, `failed_at timestamptz NULL`, `failure_code text NULL`
- Unique `(notification_recipient_id, attempt_number)`. Do not mark delivered based only on provider acceptance.

#### `webhook_events`
- `id uuid PK`, `provider_id uuid NOT NULL FK integration_providers(id)`, `provider_event_id text NOT NULL`, `event_type varchar(80) NOT NULL`, `received_at timestamptz NOT NULL`
- `signature_valid boolean NOT NULL`, `processing_status varchar(24) NOT NULL`, `payload_reference text NULL`, `processed_at timestamptz NULL`, `correlation_id uuid NULL`
- Unique `(provider_id, provider_event_id)`. Keep payload only as long as needed for verification/reconciliation, under approved retention.

#### `integration_failures`
- `id uuid PK`, `provider_id uuid NOT NULL FK integration_providers(id)`, `webhook_event_id uuid NULL FK webhook_events(id)`
- `failure_type varchar(40) NOT NULL`, `reason text NOT NULL`, `first_seen_at timestamptz NOT NULL`, `last_attempt_at timestamptz NULL`, `retry_count integer NOT NULL CHECK (retry_count >= 0)`, `status varchar(24) NOT NULL`, `resolved_at timestamptz NULL`.

### 5.8 Audit, idempotency, retention, and reporting

#### `audit_events`
- `id uuid PK`, `actor_type varchar(20) NOT NULL CHECK (actor_type IN ('USER','SYSTEM','SERVICE','ANONYMOUS'))`
- `actor_user_account_id uuid NULL FK user_accounts(id)`, `initiating_user_account_id uuid NULL FK user_accounts(id)`
- `action varchar(100) NOT NULL`, `target_type varchar(80) NOT NULL`, `target_id uuid NULL`
- Explicit optional scope FKs: `district_id`, `church_id`, `department_id`, with zero or one populated; scope can be absent for truly global/system events.
- `occurred_at timestamptz NOT NULL`, `reason text NULL`, `correlation_id uuid NULL`, `safe_change_summary jsonb NULL`
- CHECK actor identity rules: USER actor requires actor user ID; SYSTEM/SERVICE/ANONYMOUS must not be misrepresented as a human actor. Delegated activity stores initiating user separately from represented subject.
- Partitioning by time is a future operational choice. If partitioned, global uniqueness and FK limitations must be considered before adoption.

#### `audit_access_events`
- `id uuid PK`, `accessing_user_account_id uuid NOT NULL FK user_accounts(id)`, `audit_event_id uuid NULL FK audit_events(id)`
- `access_action varchar(30) NOT NULL`, `purpose text NOT NULL`, explicit scope FKs, `occurred_at timestamptz NOT NULL`, `exceptional_access boolean NOT NULL DEFAULT false`.
- Audit access is itself auditable. Restrict read permissions separately from write path.

#### `idempotency_records`
- `id uuid PK`, `key_digest text NOT NULL`, `actor_user_account_id uuid NOT NULL FK user_accounts(id)`
- `operation_code varchar(100) NOT NULL`, explicit resource scope FKs, `request_fingerprint text NOT NULL`
- `status varchar(20) NOT NULL`, `created_at timestamptz NOT NULL`, `lease_expires_at timestamptz NULL`, `completed_at timestamptz NULL`, `safe_result_reference text NULL`
- Unique composite over actor, operation, scope identity, and key digest. A normalized scope identity strategy is required because nullable columns behave specially in ordinary unique constraints; use PostgreSQL 15+ `NULLS NOT DISTINCT` only if confirmed version support, or separate partial unique indexes per scope shape.
- Store safe response reference, not raw headers, cookies, tokens, or sensitive response bodies.

#### `retention_policies`
- `id uuid PK`, `record_category varchar(60) NOT NULL`, `duration interval NULL`, `trigger_code varchar(60) NULL`, `required_action varchar(30) NOT NULL`, `legal_basis text NULL`, `approving_authority text NULL`, `version varchar(40) NOT NULL`, `effective_from timestamptz NOT NULL`, `effective_to timestamptz NULL`, `status varchar(20) NOT NULL`
- A policy with unknown/unapproved duration must not drive permanent deletion.

#### `retention_holds`
- `id uuid PK`, `record_category varchar(60) NOT NULL`, `reason text NOT NULL`, `issued_by_user_account_id uuid NOT NULL FK user_accounts(id)`, `approved_by_user_account_id uuid NULL FK user_accounts(id)`
- `created_at timestamptz NOT NULL`, `released_at timestamptz NULL`, `release_reason text NULL`, `status varchar(20) NOT NULL`
- Target binding must be enforceable. Do not implement a free-form `target_type + target_id` as if it were a real FK. Physical implementation must select either (a) target-specific link tables for each covered record class or (b) a shared retention-subject anchor with real FKs from retained records.

#### `retention_actions`
- `id uuid PK`, `retention_policy_id uuid NOT NULL FK retention_policies(id)`, `initiated_by_user_account_id uuid NOT NULL FK user_accounts(id)`, `approved_by_user_account_id uuid NULL FK user_accounts(id)`
- `target_binding_id uuid NOT NULL` referencing the selected enforceable target-binding model, `action varchar(24) NOT NULL`, `reason text NOT NULL`, `executed_at timestamptz NULL`, `outcome varchar(24) NOT NULL`, `verification_reference text NULL`
- No destructive action for a target covered by an active hold.

#### `report_definitions`, `report_runs`, and `report_export_audits`
- Definitions: `id uuid PK`, `code varchar(80) NOT NULL UNIQUE`, `version integer NOT NULL`, `classification varchar(24) NOT NULL`, `status varchar(20) NOT NULL`.
- Runs: `id uuid PK`, `report_definition_id uuid NOT NULL FK report_definitions(id)`, `requested_by_user_account_id uuid NOT NULL FK user_accounts(id)`, explicit scope FKs, `status varchar(24) NOT NULL`, `requested_at timestamptz NOT NULL`, `completed_at timestamptz NULL`, `output_object_key text NULL`, `expires_at timestamptz NULL`.
- Export audit: `id uuid PK`, `report_run_id uuid NOT NULL FK report_runs(id)`, `actor_user_account_id uuid NOT NULL FK user_accounts(id)`, `format varchar(20) NOT NULL`, `exported_at timestamptz NOT NULL`, `destination_classification varchar(24) NOT NULL`.
- Every report execution rechecks authorization. Export objects use protected storage and approved retention.

## 6. Critical constraints and enforcement matrix

| Invariant | Database enforcement proposal | Application/transaction requirement |
|---|---|---|
| One account per member | Unique FK on `members.user_account_id`, NOT NULL | Provision account and member consistently |
| One active category | Partial unique index on active current assignment | Validate eligibility and record transition reason |
| One current church | Partial unique index on active current membership | Transfer closes old and opens new atomically |
| Department membership uniqueness | Partial unique index by member/department | Check eligibility and church-transfer policy |
| No overlapping appointment | Exclusion constraint over scope/position/time where feasible | Lock position/scope and authorize approval |
| Scope target validity | Real FKs plus exactly-one CHECK | Verify scope is allowed for role/resource |
| Event capacity | Not safely enforced by simple CHECK | Atomic capacity reservation/row lock |
| Event registration uniqueness | Partial unique index | Recheck deadline, approval, and capacity |
| Attendance duplicate | Partial unique indexes for event and session modes | Serialize cross-mode check to prevent mixed double count |
| Session belongs to event | Composite unique key and composite FK | Validate session is open |
| Submitter cannot approve | Not a simple row CHECK | Transactionally compare actors; independent approver authorization |
| Account/transaction currency match | Composite FK to account currency or trigger | Validate payment provider amount/currency |
| Reversal not over original | Transactional aggregate constraint/locked original | Serialize reversal and preserve posted original |
| Webhook unique per provider | Unique `(provider_id, provider_event_id)` | Verify signature and transition order |
| Notification logical dedupe | Unique logical key | Retry with same logical key |
| Idempotency key binding | Unique composite key | Atomic claim, fingerprint comparison, safe replay |
| Audit append-only | DB grants/restricted owner; optional trigger preventing UPDATE/DELETE | Separate audited read path |
| Retention hold blocks action | Enforceable target FK and locked hold check | Check holds in same transaction as action |
| No guardian account delegation | No such relationship or delegation model | Tests reject shared/guardian login workflows |

## 7. Indexing strategy

Create indexes for:
- Every FK used for joins or delete/update checks, especially high-volume child tables.
- Login lookup and unique normalized login identifier.
- Member number and member-to-account lookup.
- Current category and church membership partial unique predicates.
- Appointment lookup by position/scope/status/effective interval.
- Role assignments and denies by user, permission, and scope.
- Event lists by owner scope and start time; registrations by event/status; sessions by event/start time.
- Attendance by event/member/time and session/member.
- Financial transactions by account/date/status/reference; approvals by transaction/time; payments by provider reference/status.
- Credential issuances by member/definition/status.
- Notifications by status/scheduled time; delivery attempts by recipient/status; webhook processing by provider/status/received time.
- Audit by occurred time, actor, target, and scope. Add retention/partitioning only after volume and query patterns are measured.
- Idempotency by unique request identity and expiry cleanup.
- Retention policies/holds by category/status/target binding.
- Report runs by requester/status/created time.

Do not add indexes speculatively to every column. Validate query plans with realistic data and `EXPLAIN (ANALYZE, BUFFERS)` in a non-production environment.

## 8. Transaction, concurrency, and immutability strategy

- Use a database transaction for every critical multi-record state transition identified in the conceptual ERD.
- Use row-level locking (`SELECT ... FOR UPDATE`) for capacity counters, session rotation, account reversals, and other serialized aggregates.
- Use unique/exclusion constraints as the final defense against concurrent duplicates.
- Use serializable isolation only for workflows that need it and have retry handling; default to READ COMMITTED with explicit locks and constraints where sufficient.
- Do not rely on application pre-checks without a database constraint or lock.
- Use an outbox table for durable notification/integration dispatch where the business mutation and message scheduling must commit together. Outbox design must be included in the next technical implementation plan, not improvised in a controller.
- Treat webhook delivery as at-least-once. Deduplicate by provider event identity and validate business transition order.
- Make audit inserts part of the same transaction as the protected business mutation when the audit event is required for the mutation to be considered complete.
- Posted finance records and audit events are append-only from the application perspective. Corrections create linked records.

## 9. Financial design blockers

The conceptual ERD intentionally leaves accounting sign convention and some workflow details unresolved. Before finalizing finance DDL, obtain an approved accounting policy covering:
- Transaction amount sign convention and transaction types.
- Whether transactions are single-amount records or multi-line accounting entries.
- Partial payments, allocation, overpayment, refunds, failed/returned payments.
- Full versus partial reversals and cumulative reversal control.
- Payment execution versus accounting posting responsibilities.
- Approval thresholds, multi-level approval, and budget enforcement.
- FX rates, rate source, conversion timestamp, and reporting treatment.

Until approved, retain `numeric(19,4)` as a precision proposal only. Do not seed transaction categories or enforce amount sign rules based on assumptions.

## 10. Privacy, retention, and child account safeguards

- Individual account per member remains mandatory. The model contains no guardian account, shared login, or delegated guardian login.
- Do not collect date of birth, address, emergency contact, or identity documents unless the approved product requirement and safeguarding policy justify the collection.
- The process for younger members using individual accounts requires a safe, approved onboarding policy. This document does not invent age thresholds or identity-verification requirements.
- Avoid IP/device metadata retention beyond an approved security purpose and schedule.
- Store evidence and exports in private object storage. Database rows hold opaque object keys, not public URLs.
- Retention schedules require an approved basis and period. Unknown periods disable automated permanent deletion.
- Retention hold target binding remains a physical-design decision that must be resolved before implementing holds.
