- Date: 2026-11-12
- Governing decision: OD-08 approved 2026-11-12
- Status: **PHYSICAL-TIME SEMANTICS PROPOSAL; FIELD-LEVEL REVIEW OPEN**

## 1. Purpose

This document reconciles the CPERD-03 timestamp and timezone columns with OD-08. It defines the difference between calendar dates, exact instants, local scheduling input and trusted system timestamps.

## 2. Static inventory

- TIMESTAMPTZ columns: 118 candidate fields.
- DATE columns: 3 fields.
- Timestamp without time zone: 0.
- Explicit timezone identifier columns: districts.timezone, events.timezone and event_sessions.timezone.
- Recurrence-rule columns: 0.

The DATE fields are:
- members.date_of_birth
- appointments.term_start
- appointments.term_end

The three timezone identifier fields are text values and require IANA timezone validation. A fixed UTC offset such as +01:00 is not a substitute for an IANA zone identifier.

## 3. Storage and conversion rules

1. Persist every exact instant as PostgreSQL TIMESTAMPTZ.
2. Persist exact instants in UTC. PostgreSQL TIMESTAMPTZ stores an instant; presentation uses the authorized IANA timezone.
3. Use DATE for calendar-only values such as date of birth and appointment term boundaries. Do not convert calendar dates to midnight UTC.
4. Use IANA timezone identifiers for local scheduling and recurrence semantics.
5. Never calculate recurring local schedules by repeatedly adding a fixed 24-hour interval to a UTC instant.
6. Resolve local wall-clock input using the selected IANA timezone and current IANA timezone database.
7. Reject nonexistent local times caused by timezone transitions. For ambiguous repeated local times, require an explicit disambiguation/offset or a documented deterministic rule. Do not silently guess.
8. Store both the resulting UTC instant and the applicable IANA zone wherever future display or recurrence interpretation depends on the original local schedule.

## 4. Timezone field ownership

| Field | Meaning | Required validation | Open decision |
|---|---|---|---|
| districts.timezone | Authoritative timezone for district-level local scheduling and presentation defaults | Must resolve to a valid IANA zone identifier | Exact district timezone source/owner and change history |
| events.timezone | Timezone used to interpret event-local schedule input | Must resolve to a valid IANA zone identifier | Whether event timezone is fixed at approval or may change through a material event change |
| event_sessions.timezone | Timezone used for the session's local schedule | Must resolve to a valid IANA zone identifier | Whether session timezone must equal event timezone or an authorized session override is permitted |

Do not hardcode Africa/Lagos or any other timezone as a universal default. The owning authority must explicitly supply the correct IANA identifier.

## 5. Timestamp source classification

### 5.1 Trusted system/audit timestamps

The following classes must be generated by a trusted server, worker or database. Client-supplied timestamp values are prohibited:
- created_at and updated_at;
- authentication/session issue, activity, consumption, revocation and expiry timestamps;
- audit_events.occurred_at and audit_access_events.occurred_at;
- attendance_records.recorded_at and attendance correction request/approval times;
- event approval/change decision timestamps;
- registration creation/cancellation timestamps;
- notification/outbox/webhook receipt, processing, delivery and retry timestamps;
- integration failure first-seen, attempt and resolution timestamps;
- report run/export request, start, completion, export and expiry timestamps;
- retention hold/action timestamps;
- idempotency claim, lease, completion, response expiry and tombstone timestamps.

For created_at, the physical candidate uses transaction_timestamp() as a trusted database default. For updated_at, the candidate uses transaction_timestamp() on insert and a trusted update trigger on update. The trigger function, role privileges and bypass protection remain subject to final physical review.

For other trusted timestamps, the owning server/worker/audit writer assigns the timestamp inside the authorized transaction. No API request accepts a client-selected value for these fields.

### 5.2 Authorized business-effective timestamps

Fields such as effective_from/effective_to, appointment approved/rejected/terminated times, retention eligibility and other lifecycle timestamps are set by the owning workflow when the transition is authorized. They are not arbitrary client timestamps. The server validates transition authority, ordering and consistency.

### 5.3 Local schedule input

Events and event sessions accept local schedule input with an explicit IANA timezone. The application converts the accepted local schedule into exact UTC TIMESTAMPTZ instants. Registration opening/closing times follow the event timezone unless a separately approved contract defines otherwise.

## 6. Recurrence boundary

The current CPERD-03 column register contains no recurrence-rule field. Recurring event scheduling is therefore not represented as an active v1 physical capability.

If recurring schedules are later included, the design must preserve:
- the local recurrence rule;
- the IANA timezone;
- the local wall-clock time;
- effective start/end boundaries;
- the policy for timezone database updates and DST gaps/folds.

A future recurrence feature requires scope and physical-design review. Do not infer a recurrence rule from a sequence of UTC timestamps.

## 7. Clock synchronization and audit integrity

- Production application servers, workers and database hosts must use synchronized system clocks through NTP or an equivalent trusted time service.
- Audit timestamps must be generated by a trusted server/database source.
- The application must not accept user-supplied occurred_at, created_at, updated_at, recorded_at, issued_at or similar audit timestamps.
- Timestamp corrections, if ever required, must be represented as new audited facts, not silent backdating of existing audit evidence.
- Transaction retries must not duplicate external effects or fabricate new business timestamps for an already committed event.

## 8. Closure requirements

1. Confirm the authoritative timezone source for every district.
2. Confirm whether event sessions inherit event timezone or allow authorized overrides.
3. Map every TIMESTAMPTZ column to trusted system, business-effective or local-schedule semantics.
4. Confirm all API contracts reject client-supplied system/audit timestamps.
5. Specify the exact updated_at trigger target list and function/privilege boundary.
6. Confirm DST ambiguity handling in the application contract.
7. Confirm recurring schedules remain excluded from v1 or approve a separate recurrence design.
8. Reconcile the 118 TIMESTAMPTZ and 3 DATE fields against the final column register.
